# SOC Incident Investigation & Alert Triage

## Objective

Investigate and analyse security alerts generated by Elastic SIEM following controlled authentication attack simulations against WindowsEndpoint.

The objective was to demonstrate a structured Security Operations Centre (SOC) investigation workflow, including:

- Reviewing and triaging security alerts in Elastic Security.
- Analysing Windows authentication events using Kibana Discover.
- Identifying targeted accounts, source IP addresses and authentication methods.
- Correlating related security events to establish the sequence of activity.
- Evaluating the nature and potential impact of detected authentication attempts.
- Documenting investigation findings and applying appropriate alert dispositions.

The investigations focused on repeated failed Windows authentication events detected by the custom **Repeated Windows Failed Logons** rule.

## Investigation Scope

Three controlled authentication scenarios were examined:

| Scenario | Activity | Investigation Focus |
|---|---|---|
| 1 — Initial Detection Validation | Failed authentication attempts targeting `FakeSOCUser` | Verify that the detection rule generated the expected alert |
| 2 — Remote SMB Authentication | Repeated failed logons originating from Kali Linux (`192.168.56.102`) | Identify the remote source and validate the detected network authentication activity |
| 3 — Hydra Password Guessing | Three failed logons followed by successful authentication against `HydraLabUser` | Correlate Event IDs 4625 and 4624 and establish the authentication outcome |

All three scenarios were intentionally generated within the isolated VirtualBox homelab.

The investigations were conducted using Windows Security logs, Kibana Discover, Elastic Security alerts and analyst investigation notes.

The observed activity was authorised laboratory testing, not an actual security breach. The resulting alerts were investigated and closed after confirming their origin and purpose.

## SOC Alert Triage Workflow

### 1. Alert Identification

Security alerts were reviewed through **Kibana → Security → Alerts**.

The custom detection rule, **Repeated Windows Failed Logons**, generated alerts when three or more Windows Event ID 4625 records targeted the same username within the configured detection window.

The initial triage involved reviewing the following alert information:

| Alert Attribute | Investigation Purpose |
|---|---|
| Rule Name | Identify which detection generated the alert |
| Severity | Understand the initial alert classification |
| Risk Score | Review the rule's assigned risk assessment |
| Target Username | Identify the account experiencing authentication failures |
| Threshold Count | Verify how many matching events triggered the alert |
| Timestamp | Establish when the activity was detected |
| Alert Status | Track whether the alert remained open or had been closed |

The generated alerts were classified as **Medium severity**, with a risk score of **47**.

### 2. Detection Validation

The alert details were examined to determine whether the activity matched the configured detection logic.

The following Elastic Security fields were reviewed:

- `kibana.alert.rule.name` — identifies the detection rule.
- `kibana.alert.threshold_result.count` — records the number of matching events contributing to the threshold alert.
- `winlog.event_data.TargetUserName` — identifies the targeted account where available in the alert fields.

The threshold result was confirmed as **3**, matching the detection rule's configuration.

This established that the alert was generated as expected.

### 3. Supporting Log Investigation

Following alert identification, Kibana Discover was used to examine the underlying Windows authentication events.

The `logs-*` data view was selected, and KQL searches were used to identify relevant records.

**Failed authentication events:**

`agent.name:"WindowsEndpoint" AND winlog.event_id:4625`

**Successful authentication events:**

`agent.name:"WindowsEndpoint" AND winlog.event_id:4624`

The investigation considered:

- Targeted usernames.
- Event timestamps.
- Authentication success or failure.
- Source IP addresses and workstation names.
- Logon types.
- Authentication protocols.

These details helped establish the context of the authentication activity and identify whether related events shared a common source.

### 4. Event Correlation

Individual authentication events were compared to establish the sequence of activity.

During the Hydra simulation, three failed authentication events were followed by one successful authentication event targeting `HydraLabUser`.

The Windows Security records showed that the events originated from the Kali attacker VM at `192.168.56.102`.

This demonstrated the importance of examining surrounding events rather than relying exclusively on the original detection alert.

The custom rule detected the repeated failures; the subsequent successful authentication was identified through further log analysis.

### 5. Investigation Findings & Alert Disposition

Following the analysis, the findings were recorded in the **Notes** section of the Elastic Security alert details.

Investigation notes documented:

- The authentication activity observed.
- The targeted account and originating system.
- Relevant Windows Event IDs.
- The relationship between the events and the controlled lab simulation.
- The investigation conclusion.

The alerts were subsequently changed from **Open** to **Closed** after the activity was confirmed as expected, authorised testing.

### 6. Triage Outcome

The investigation workflow demonstrated how an analyst can progress from an automated detection to a documented conclusion.

**Security Alert → Validate Detection → Review Supporting Logs → Correlate Events → Document Findings → Close Alert**

The process reinforced that an alert represents activity requiring assessment, rather than automatic confirmation of a security compromise.

In each investigated scenario, the observed activity was consistent with the controlled authentication testing conducted within the homelab.

## Investigation 1 — Remote SMB Authentication Failures

### Incident Overview

On 12 October 2026, the custom **Repeated Windows Failed Logons** detection rule generated a security alert following three unsuccessful SMB authentication attempts against WindowsEndpoint.

The attempts targeted the `FakeSOCUser` account and originated from the Kali Linux attacker VM.

The investigation aimed to identify the source of the authentication failures, validate the detection and determine whether the activity represented unauthorised access or controlled testing.

### Alert Details

| Attribute | Observed Value |
|---|---|
| Detection Rule | Repeated Windows Failed Logons |
| Alert Severity | Medium |
| Risk Score | 47 |
| Target Account | `FakeSOCUser` |
| Failed Authentication Events | 3 × Event ID 4625 |
| Threshold Count | 3 |
| Source IP Address | `192.168.56.102` |
| Source Workstation | `KALI` |
| Destination | WindowsEndpoint (`192.168.56.101`) |
| Logon Type | 3 — Network |
| Authentication Protocol | NTLM |
| Network Service | SMB / TCP 445 |

### Investigation Process

**1. Alert Review**

The generated alert was examined in Elastic Security.

The targeted account, assigned severity and detection rule were reviewed to confirm the reason for the alert.

The threshold result showed that three authentication failures had satisfied the configured detection conditions.

**2. Windows Security Log Analysis**

Windows Event ID 4625 records were examined to identify the authentication details.

The events showed that the failed authentication attempts targeted `FakeSOCUser` and used Logon Type 3, indicating network-based authentication.

Further analysis identified:

- Source workstation: `KALI`
- Source IP: `192.168.56.102`
- Authentication package: NTLM
- Logon process: `NtLmSsp`

These fields linked the failed authentication activity to the Kali Linux VM.

**3. Source Attribution**

The source IP address was compared with the documented homelab network configuration.

The address `192.168.56.102` matched the designated Kali attacker VM.

The SMBClient test output also confirmed that authentication using deliberately invalid credentials had been rejected with:

`NT_STATUS_LOGON_FAILURE`

Together, the attacker-side output and Windows Security records established the source and outcome of the activity.

**4. SIEM Correlation**

Kibana Discover was used to verify that the three Event ID 4625 records were successfully collected by Elastic Agent and indexed in Elasticsearch.

The custom detection rule subsequently generated the expected security alert.

This confirmed that remote authentication activity was visible to the monitoring infrastructure.

### Investigation Findings

The investigation established that:

- Three failed network authentication attempts targeted the same account.
- The attempts originated from the designated Kali attacker VM.
- The activity used SMB over TCP port 445 and NTLM authentication.
- Windows recorded the attempts as Event ID 4625.
- The Elastic detection rule correctly identified the repeated failures.
- No successful authentication was observed during this SMBClient testing scenario.

### Analyst Disposition

The activity was confirmed as an authorised attack simulation within the isolated homelab.

An investigation note was recorded in Elastic Security documenting the authentication failures, source IP address, logon type, protocol and test context.

The alert was subsequently closed.

**Classification:** True-positive detection of expected laboratory activity.

The detection was technically correct because the authentication failures occurred and matched the rule conditions. However, the activity was intentionally generated for testing rather than representing a real-world security incident.

### Investigation Outcome

The investigation successfully demonstrated the ability to identify, analyse and attribute suspicious authentication activity using Windows Security logs and Elastic SIEM.

The exercise provided practical experience in alert triage, source attribution, event correlation, investigation documentation and alert closure.

It also established a repeatable investigation workflow for the more advanced Hydra password-guessing scenario.

## Investigation 2 — Hydra Password-Guessing and Successful Authentication

### Incident Overview

On 12 October 2026, a controlled Hydra password-guessing simulation generated repeated authentication failures against the temporary Windows account `HydraLabUser`.

The activity originated from the Kali Linux attacker VM at `192.168.56.102` and targeted WindowsEndpoint over SMB (TCP 445).

The custom **Repeated Windows Failed Logons** detection rule identified the failed authentication activity and generated a security alert.

Further investigation revealed that the failed attempts were followed by a successful authentication using valid credentials.

The investigation aimed to establish the complete authentication sequence, identify its source, determine the outcome and document the findings.

### Alert Details

| Attribute | Observed Value |
|---|---|
| Detection Rule | Repeated Windows Failed Logons |
| Severity | Medium |
| Risk Score | 47 |
| Target Account | `HydraLabUser` |
| Source IP Address | `192.168.56.102` |
| Source Workstation | `KALI` |
| Destination | WindowsEndpoint (`192.168.56.101`) |
| Network Service | SMB / TCP 445 |
| Authentication Protocol | NTLM |
| Logon Type | 3 — Network |
| Failed Authentication Events | 3 × Event ID 4625 |
| Successful Authentication Events | 1 × Event ID 4624 |

### Investigation Process

**1. Security Alert Review**

The alert generated by the custom detection rule was examined through Elastic Security.

The investigation focused on the targeted username, rule severity, risk score and repeated authentication failures.

The rule identified the failed authentication activity affecting `HydraLabUser`.

However, the detection rule was configured specifically for Event ID 4625 and did not independently identify the subsequent successful authentication.

Further investigation was therefore required.

**2. Windows Authentication Log Analysis**

Kibana Discover was used to examine authentication events associated with `HydraLabUser`.

The `logs-*` data view provided access to the Windows Security events collected through Elastic Agent.

The investigation identified four relevant events:

| Time — 12 October 2026 | Event ID | Authentication Result |
|---|---|---|
| 21:31:36 | 4625 | Failed |
| 21:31:38 | 4625 | Failed |
| 21:31:41 | 4625 | Failed |
| 21:31:43 | 4624 | Successful |

The events established the following sequence:

**Failed → Failed → Failed → Successful**

The successful authentication occurred approximately seven seconds after the first recorded failure.

**3. Source Attribution**

The Windows authentication records were examined to identify the originating system.

The following information was confirmed:

- Target account: `HydraLabUser`
- Source workstation: `KALI`
- Source IP address: `192.168.56.102`
- Logon type: 3 — Network
- Authentication protocol: NTLM

These findings linked the authentication sequence to the Kali attacker VM.

The source information was consistent with the documented homelab architecture and the controlled Hydra simulation.

**4. Successful Authentication Verification**

The successful Event ID 4624 was examined separately to establish what occurred after the failed attempts.

Windows recorded a successful Logon Type 3 authentication for `HydraLabUser`.

This confirmed that valid credentials had been accepted for a network authentication session.

The event did not establish that the account obtained administrative privileges or an interactive desktop session.

The successful authentication was independently consistent with Hydra's output, which reported that a valid credential had been identified.

**5. Event Correlation**

The three failed authentication events and subsequent successful authentication were correlated using:

- Target username.
- Event timestamps.
- Source IP address.
- Source workstation.
- Logon type.
- Authentication protocol.

The evidence established that the authentication failures and successful login were associated with the same controlled testing scenario.

This demonstrated the importance of examining related security events beyond the original alert.

### Investigation Findings

The investigation established that:

1. Three failed SMB network authentication attempts targeted `HydraLabUser`.
2. The attempts originated from the Kali attacker VM.
3. Windows recorded the failures as Event ID 4625.
4. The fourth authentication attempt succeeded and generated Event ID 4624.
5. The successful authentication used Logon Type 3 and NTLM.
6. Elastic Agent successfully collected the authentication telemetry.
7. The custom detection rule identified the repeated failures.
8. The relationship between the failures and subsequent success was established through analyst investigation.

### Analyst Disposition

The activity was confirmed as an intentional, authorised password-guessing simulation against a temporary lab account.

An investigation note was added to the Elastic Security alert documenting:

- The three failed authentication attempts.
- The subsequent successful network authentication.
- The targeted account and originating system.
- The relevant Windows Security Event IDs.
- The confirmed controlled-testing context.

The alert was subsequently marked **Closed**.

**Classification:** True-positive detection of authorised laboratory activity.

The detection accurately identified the repeated authentication failures. Although the test resulted in successful authentication, the activity was authorised and confined to the homelab.

### Investigation Outcome

The investigation successfully identified and correlated failed and successful Windows authentication events following a controlled password-guessing simulation.

The exercise demonstrated practical SOC investigation skills, including:

- Security alert triage.
- Windows authentication event analysis.
- Source attribution.
- Timeline reconstruction.
- Correlation of Event IDs 4625 and 4624.
- Verification of authentication outcomes.
- Evidence-based incident documentation.
- Alert disposition and closure.

The investigation also highlighted a limitation of the existing detection rule: it identified repeated authentication failures but required additional analysis to recognise a subsequent successful login.

This finding provides a basis for future detection improvements involving failure-to-success authentication correlation.

## Investigation Results & Lessons Learned

### Investigation Summary

Three controlled authentication scenarios were examined to validate the SOC monitoring and investigation capabilities of the Elastic SIEM.

| Scenario | Detection Result | Investigation Outcome |
|---|---|---|
| Initial failed-logon test | Alert triggered after three failures against `FakeSOCUser` | Confirmed detection logic worked as configured |
| Remote SMB authentication | Alert triggered following repeated network authentication failures | Identified Kali as the source and confirmed unsuccessful authentication |
| Hydra password guessing | Alert triggered following three failed authentication attempts | Correlated the failures with a subsequent successful network authentication |

All investigated alerts were confirmed as expected results of authorised laboratory testing.

### Key Achievements

- Investigated security alerts generated by a custom Elastic Security detection rule.
- Validated alert thresholds and examined relevant detection fields.
- Used Kibana Discover to identify and analyse underlying Windows authentication records.
- Correlated authentication events using usernames, timestamps, source IP addresses and logon types.
- Identified the Kali attacker VM as the source of remote authentication activity.
- Distinguished unsuccessful authentication from successful network authentication.
- Recorded investigation findings and closed the resulting security alerts.

### Lessons Learned

**1. Alerts require investigation**

An automated security alert identifies activity that meets a detection condition, but additional evidence is required to determine the cause, outcome and significance of that activity.

**2. Event correlation provides greater context**

Examining Event IDs 4625 and 4624 together revealed the successful authentication that followed the Hydra password-guessing attempts.

The original detection rule identified repeated failures but did not automatically correlate the subsequent success.

**3. Source attribution strengthens investigations**

Windows authentication records containing source IP addresses, workstation names and logon types helped establish where the activity originated.

Comparing these records with the documented network architecture supported source attribution.

**4. Detection accuracy and incident severity are different considerations**

The custom rule correctly detected repeated authentication failures, making the alerts valid detections.

However, the activity was intentionally generated within an authorised test environment and did not constitute an actual security breach.

**5. Investigation documentation supports accountability**

Recording findings, supporting evidence and alert dispositions created an auditable record of the investigation process.

Clear documentation also makes it possible for another analyst to understand how a conclusion was reached.

### Opportunities for Improvement

The investigations identified several opportunities to strengthen the monitoring environment:

- Develop detection logic to correlate repeated authentication failures with subsequent successful logons.
- Include source IP addresses and workstation information in authentication-based detection analysis.
- Evaluate account lockout policies to reduce password-guessing risk.
- Develop a consistent incident response checklist for repeatable alert triage.
- Improve the presentation of investigation timelines and supporting evidence.

These findings will inform the risk assessment and remediation recommendations in Section 7.

### Conclusion

The SOC investigations successfully demonstrated the process of identifying, validating, analysing and documenting suspicious authentication activity using Elastic Security.

The most significant finding was the identification of a successful network authentication following three failed password attempts during the Hydra simulation.

The investigation demonstrated that automated detection provides an important starting point, but effective SOC analysis requires additional log review, event correlation and evidence-based judgement.

The completed investigations provide the foundation for the next project stage: **Risk Assessment, Remediation & ISO 27001 Control Mapping**.
